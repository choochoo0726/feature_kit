feature_kit · design overview

From daily time series to alpha signals

feature_kit is a Polars library that turns panels of daily data, such as alternative-data KPIs, into forecast features for downstream alpha models. Every signal is built by four composable stages that share one column configuration.

Architecture

Four stages, each an abstract base class with a single compute() method. Each stage can be used alone or chained by FeatureBuilder.

Stage 1

Base feature

Benchmark

  • ZeroBenchmark

  • CohortRollingSum…
  • IBESConsensus…
Stage 3

Comparison

How far is the feature from the benchmark?

  • Difference, Sign, Ratio (pointwise)
  • ZScore, Rank, Residual (rolling, per entity)
Stage 4

Transformation

Make the signal model-ready.

  • Clip
  • Winsorize (per date by default)
  • RampUp / RampDown (by entity age)

Data contract

Every frame is long format: one row per entity per date. Stages communicate only through column names.

Param

Param(keys=["specid"], metrics=["SALES", "TXN"], date_col="DATADATE")

The single source of truth for column names. keys scope every per-entity operation (rolling windows, z-scores, ranks, residuals); metrics become the prefix of every derived column.

Pairing rules

Which feature column is compared with which benchmark column. Decided for each benchmark column in comparisons._pair_cols.

Design decisions

The choices that shape how values are computed.

  • Lags are date shifts, not row shifts.A lagged value is found by adding N days to the date column and joining back on keys + date. A missing day gives null instead of silently pulling the wrong day's value.
  • YoY offset is 364 days.52 whole weeks keep the day of week aligned, which matters for spending data with strong weekly seasonality.
  • Column names carry lineage.Double-underscore names record how each column was built. Benchmarks find their inputs by substring, and comparisons pair columns by prefix, so no extra metadata is passed between stages.
  • Builder is a full cross product.Every comparison runs against every benchmark. Simple to reason about, but output width grows multiplicatively: metrics × windows × benchmark columns × comparisons.
  • Point-in-time by default.Winsorize uses per-date quantiles, IBES uses a backward as-of join, and rolling statistics only look backwards. Full-sample winsorizing is opt-in (scope="pooled").
  • Builder output is signals only.Columns a transformation needs (e.g. an age column) are joined from the raw input just for that step and dropped afterwards.
  • Polars throughout.Vectorised expressions with .over(keys) for per-entity work, including the rolling rank and rolling OLS residual comparisons. Polars is the only runtime dependency.
  • Calendar windows with a coverage rule.Rolling sums cover exact calendar days; missing days count as zero, and a window is null below min_coverage (default 80% of days) or before the entity has a full window of history.
  • Zero denominators give null.Growth rates, ratios and projections return null rather than inf/NaN, so downstream models never see infinities.

Extending

Add a component by subclassing a base class and following the naming convention.

Contract per stage

  • BaseFeature: return keys + date + {METRIC}__{FEATURE}__{WINDOW}.
  • Benchmark: one row per base row; name derived columns {feature}__{SUFFIX}.
  • Comparison: reuse _pair_cols; name outputs {base}__VS__{bench}__{NAME}.
  • Transformation: same columns in and out; optional params and required_columns.

Example

class ConstantBenchmark(Benchmark):
    def __init__(self, params, value):
        self.params, self.value = params, value

    def compute(self, base_df, raw_df, external_dfs=None):
        k, d = self.params.keys, self.params.date_col
        return base_df.select([*k, d]).with_columns(
            pl.lit(self.value).alias("CONSTANT_BENCHMARK"))

Known limitations

Current behaviour to account for. Details are in the docs site's Known limitations page.

  • Missing days count as zero in rolling sums (up to the min_coverage threshold); raise it if a missing day means "no data" rather than "no activity".
  • Comparison lookbacks (z-score, rank, residual) count the last W observations, not W calendar days.
  • Cohort benchmark includes the entity itself unless exclude_self=True.
  • Pooled winsorizing (scope="pooled") uses future data; the default per-date scope does not.
